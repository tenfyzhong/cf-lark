# Encrypted workflow state storage

Workflow metadata remains encrypted in Durable Object SQLite. State and completed output that exceed the inline threshold are stored as immutable, chunk-encrypted R2 objects through the existing artifact service. These internal objects use a workflow-specific owner namespace, never the grant's public artifact owner, and consume the same aggregate 2 GB storage and monthly operation budgets. Read-only workflows do not need artifact write permission for internal checkpoints.

Serialization is bounded to 32 MiB per stored record, with an explicit error above the bound. A 100000-value and 128-level nesting guard also prevents small serialized inputs from amplifying into unbounded object graphs. A streaming JSON serializer and parser avoid building a second complete plaintext JSON document. Encryption operates on bounded chunks, authenticated with the workflow owner, ID, random blob identity, and chunk position. A terminal authenticated record verifies the chunk count and byte count; truncated or reordered objects fail closed.

Blobs are written before the SQLite compare-and-swap. Losing contenders delete their staged blobs. Winning revisions register blob references and retire the prior references synchronously with the successful revision update. Active readers acquire expiring SQLite leases before decrypting a snapshot, preventing retired-blob cleanup from racing a read. Reads time out before their lease expires. Retired objects are removed after the last reader lease closes; failed cleanup remains tracked for later scheduled cleanup. Expiration deletes workflow rows and retires their blobs. Completed records discard intermediate state while retaining encrypted output for idempotent resume.

Existing inline records remain readable. Deployments that do not inject the blob service retain the previous 512 KiB inline limit. The production bootstrap injects the same artifact service and encryption instance already used by the vault.
